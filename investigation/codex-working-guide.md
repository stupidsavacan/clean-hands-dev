# Codex への申し送り：CLEAN HANDS での作業の仕方

これは、Claude（依頼文を書き、結果を確かめる側）が、このプロジェクトでどう作業してきたかをまとめたものです。修正の依頼を受けたときは、依頼文と一緒にこれを読み、同じやり方で進めてください。依頼文とこの文書が食い違うときは、依頼文を優先してください。

## 1. 役割と、ユーザーとのやりとり

- **役割分担**
  - Claude は、遊んだ記録とメモを調べて原因を突き止め、依頼文を書き、直ったかを確かめます。
  - Codex（あなた）は、ゲームの修正をします。
  - 依頼文は `outputs\m5-prototype\investigation\codex-prompt-*.md` に置きます。
- **言葉**：ユーザー（遊んで確かめる人）に向けた文章は、すべて日本語で書きます。報告、README、ゲーム内の表示、どれも同じです。
  - 短い文で書きます。1文に1つのことだけ書きます。
  - 専門用語や英語の略語は、なるべく使いません。使うときは、何のことかを書き添えます。
  - 原因は、具体的に書きます。数値・位置（x, z）・ゲーム内の時刻・記録のファイル名・コードの行を挙げます。
    - 悪い例：「判定に問題があった」
    - 良い例：「警備員が線から4.18m離れて立っていて、両方に1.65m以内まで近づける床が0か所だった」
- **頼まれたことだけ変える。**
  - 範囲の外を変える必要が出たら、変える前に、理由を書いて止まります。
  - 「ついでに直した」はしません。気づいたことは、報告の最後に「気づいたこと」として書きます。
  - キャラクターのモデルを頼まれたときは、頼まれたキャラクターだけを変えます。ほかのキャラクターを作り直してはいけません（以前、Agent 47 だけを頼まれたのに、ほかの3体まで作り直して指摘されました）。
- **ユーザーが決めたこと**
  - 捕まる仕組み（`ai.ts` の `caught`）は、2026-11-02 にユーザーの判断で HITMAN に合わせました。立入禁止はまず警告、従わなければ取り押さえ、そのときだけ捕まります。顔を知られた・犯罪を見られた・`secure` 区域では警告なしです（README「NPCの認識・戦闘・検問の修正」）。これ以上は、頼まれない限り変えません。
  - モバイル版（`outputs\m55-mobile`）は、iPad 第9世代を横に持って遊ぶ前提です（1080×810、DPR 2、タッチ）。スマートフォンの縦持ちは後回しです。
  - サイトへの公開、git のコミットとプッシュは、頼まれたときだけ行います。
- **報告は、事実どおりに書く。**
  - 確かめたことは、確かめた方法と数値と一緒に、はっきり書きます。
  - 確かめていないことは、「確かめていない」と書きます。
  - テストが失敗したら、その出力をそのまま載せます。

## 2. 原因の調べ方

順番は、いつも次のとおりです。

1. **人が遊んだ記録を見る**
   - 記録とメモ：`outputs\m5-prototype\playtest\runs\`。形式は `playtest\README.md` にあります。
   - メモ（F8）には、本文・札・写真・そのときの状態・近くの人・直前の出来事8件が入っています。写真（`*_memo<番号>.jpg`）は必ず開いて見ます。
   - 記録の `events` は数千件になることがあります。毎秒の時計（`clock.tick`）、予定（`schedule.action`）、セリフ（`dialogue.line`）、状態変化（`npc.state`）を飛ばして読むと、流れがつかめます。
2. **コードで原因の行を突き止める**：推測で直さないでください。どの関数の、どの条件で起きるかを、行番号まで特定します。
3. **再現して確かめる**：本物のゲームのコードとデータで、同じことが起きるかを確かめます（下の「3. 調査スクリプト」と「4. ブラウザでの確認」）。
4. **直す**
5. **本番のマップで確かめる**

### 過去の失敗から決めたこと

- **練習用のマップで確かめない。** 検問のテストは、練習用の `marina.json` を使っていました。そのため、本番の `hotel.json` で検問が1つも機能していないのに、テストはすべて通っていました。確かめは本番のホテルで行います。
- **途中を省略しない。** 以前のシミュレーターは、次の3つを省略していました。人が遊ぶと、失敗はほぼ全部そこで起きました。
  - 服を `dress()` で着せていた
  - 作動場所へ瞬間移動していた
  - 移動中、プレイヤーを地図の外に置いていた
  - 今は、ゲームの中の手順で服を手に入れ、ナビの道を歩く速さで歩き、周りの人を残したまま確かめます。

## 3. 調査スクリプト（.ts）を作る基準

- **作るとき**
  - 「ゲームの仕組みとして、本当にそうなるか」を示す必要があるとき。たとえば、届く・届かない、越えられる・越えられない、見える・見えない、何秒で何が起きるか。
  - 感覚や画面写真だけでは、言い切れないとき。
- **作り方**
  - 置き場所：`outputs\m5-prototype\investigation\`。名前は調べる内容にします（`checkpoint-reach.ts`、`checkpoint-gap.ts` など）。
  - 実行のしかた：`app` で `node --experimental-strip-types --no-warnings ../investigation/<名前>.ts`
  - 本物のゲームのモジュール（`../app/src/*.ts`）と、本物のデータ（`hotel.json`、`rules.json` など）を読み込みます。判定を自分で書き直さないでください。
  - ゲームと同じ判定を、同じ順番で通します。例：歩くなら、5cm刻みで `world.move` を通し、そのあと `m4.constrain` を通す。
  - 先頭のコメントに、次の3つを書きます。
    - 何を確かめるか
    - きっかけ（どのメモ・記録か。時刻と位置）
    - 実行のしかた
  - 結果は、1行に1つのJSONで出します（例：`{"route":"around the west end","upstairs":true}`）。報告にそのまま貼れるようにするためです。
  - **調査のためにゲームのコードやデータを変えてはいけません。**
  - 作ったスクリプトは消さずに残します。直したあとに流し直して、直ったことを示すのに使います。
- **テストとの違い**
  - スクリプトは、調べるためと、直る前と後を比べるためのものです。
  - 直ったことを保証し続けるのはテスト（`app\tests\`）です。スクリプトで見つけた失敗の手順は、テストにも入れます。

## 4. ブラウザでの確認

- **確かめるとき**：見た目・動き・画面の表示・タイミング・コンソールのエラーが関わるとき。
- **方法**：Playwright のヘッドレスのブラウザを使います。
  - Playwright：`C:/Users/gamit/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules/playwright`
  - Chromium：`C:/Users/gamit/AppData/Local/ms-playwright/chromium-1243/chrome-win64/chrome.exe`
  - 起動の引数：`--enable-gpu --use-gl=angle --use-angle=d3d11 --ignore-gpu-blocklist`
  - ゲームは、別のポートで配信して開きます。`outputs\m5-prototype` で `python -m http.server 8796 --bind 127.0.0.1` を実行し、`/index.html` を開きます。終わったら止めます。
  - 見えていないブラウザの画面は、1〜2fps に落ちます。タイミングの確認には使えません。
- **デバッグ用の入口** `window.__cleanHands`
  - `teleport(x, z, y=0)`：引数は順に並べます。オブジェクトを渡すと位置が壊れます。
  - `jumpTime(秒)`：ゲーム内の時刻を絶対値で指定します（「何秒進める」ではありません）。
  - `timeScale(1 か 4)`：それ以外の値はエラーになります。
  - ほかに `disguise(id)`、`view(yaw, pitch)`、`state()`、`clock()`、`director()`、`field()`（A1 の系）、`m57System()`、`combatSystem()`、`detectionSystem()`、`eventBus()`、`shoot(x, y, z)` などがあります。
  - 待つときは `modelReady` を待ち、「作戦開始」を押し、画面をクリックしてから操作します。
- **画面写真は、撮ったら必ず自分で開いて見ます。** 撮っただけで「確かめた」と書かないでください。カメラの向きがずれて、写したいものが写っていないことがよくあります。
- コンソールのエラー（`pageerror` と `console.error`）を集めて、0件かどうかを報告します。

## 5. README を書く基準

- **読む人**：開発者ではなく、遊んで確かめるユーザーです。日本語で書きます。
- **いつ書くか**：動きを変えたら、同じ作業の中でREADMEも直します。あとでまとめて、はしません。
- **形**
  - 道具のREADME（例：`playtest\README.md`）は、次の順に書きます。
    1. 何をするものか
    2. 起動のしかた
    3. 使い方（番号つきの手順）
    4. 機能ごとの節
    5. ファイルの中身の表
    6. しくみ
  - ゲームのREADMEには、修正のたびに「5.8のあと：〜の修正」のような節を足します。中身は次のとおりです。
    - 変えたこと
    - 変えた値と、それを置いたJSON
    - 足した隠し場所・予定・セリフ
    - 直したテストとその理由
    - 確かめたこと・確かめていないこと
- **書き方**
  - 1行に1つのこと。長い段落にしません。箇条書きと表を使います。
  - キーの名前は太字にします（**F8**、**Enter**、**Esc** など）。
  - 画面に出る文言は、そのまま「」で書きます。
  - できないこと・制限も書きます（例：「コインの枚数だけは変えられません」）。

## 6. コードの書き方

- **まわりに合わせる**
  - ゲームのコード（`app\src`）は、1行に詰めて書く書き方です。そのまま合わせてください。
  - コメントは英語で、なぜそうするかを短く書きます。
  - 名前の付け方・コメントの量も、まわりと同じにします。
- **値はJSONに置く。** 距離・秒数・時刻・位置・半径は、`rules.json` などに置きます。
- **`hotel.json` は手で書き換えない。** `scripts/build-hotel.ts` を直して生成します。
- **既存のテストはすべて通す。** 仕様として意図して変えたときだけ、テストを直してかまいません。そのときは、どれをなぜ直したかを報告します。
- **新しいテストの決まり**
  - 本番のホテルで確かめる。
  - 周りの人を消さない（`clearAround` しない）。
  - 服は `dress()` で着せない。
  - 瞬間移動せず、ナビの道を歩く。
  - 時間は `clock.jump` で飛ばす。
  - 採点は `ScoreLedger` と `computeResult` で行う。

## 7. 作り直しと渡し方

1. `app` で `npm test`。件数と成否を書きます。
2. `npm run build` のあと `node scripts/standalone.mjs` で、`outputs\m5-prototype\index.html` を作り直します。
3. 同じものを、依頼文で指定された名前（例：`clean-hands-m5.8-pc-playtest2-fixes.html`）でも保存します。
4. ブラウザで開き、作戦開始からプレイ画面が出ること、コンソールのエラーが0件であることを確かめます。
5. 最後に、日本語で報告します。
   - 変えたファイルの一覧
   - 依頼の項目ごとの結果
   - 確かめたこと（方法と数値）と、確かめていないこと
   - 人がもう一度遊んで確かめるべきこと

## 8. プレイテストの道具（`outputs\m5-prototype\playtest\`）

依頼で頼まれない限り、変えないでください。仕組みは知っておいてください。

- `server.py`：127.0.0.1:8795 で、ゲーム（`..\index.html`）に `playtest.js` と `debug.js` を足して配信し、記録を `runs\` に保存します。
- `playtest.js`：記録係です。
  - シナリオを選び、出来事と1秒ごとの状態を保存します。
  - F8 でメモを取ります。
  - 同じ人の同じ出来事（見つかった・目撃・通報・撃たれた）が3秒以内に続いたら、1件にまとめて回数（`repeat`）を付けます。
- `debug.js`：F9 のデバッグ画面です。
  - 体力・服・持ち物・チャンス・仕掛け・フラグ・人・時間・移動を操作できます。
  - **デバッグを使った作戦は記録しません**（それまでに保存した分も消します）。
- ゲームを作り直すと、サーバーを起動し直さなくても、次に開いたときから新しい版になります。
  - `server.py` を変えたときだけ、起動し直しが要ります。
  - `playtest.js` などを変えたときは、ユーザーに「ページを再読み込みして」と伝えます。開いたままの古いページは、古いやり方で記録し続けるためです。
- **ヘッドレスのブラウザで試すと、`runs\` に記録が作られます。** 試し終わったら、自分が作った記録だけを消します。
  - 自分の記録かどうかは、記録の `meta.userAgent` に `HeadlessChrome` が入っているかで確かめます。
  - ユーザーの記録は、頼まれない限り消しません。消すときも、メモが入っていれば、先に本文をユーザーに伝えます。

## 9. キャラクターのモデルを扱うとき

- **参考にするもの**：Astra が作ったもの（`astra-hair-repertoire`、`character-revision`、`astra-lowpoly-remodel`）を使います。
  - GPT「Sol」が作ったモデル（`lowpoly-women-study`、`sol-planes.glb` など）は、ユーザーが質が悪いと判断しています。参考にも比較にも使いません。
- **確認用のレンダーは、Astra と同じ照明にそろえる。** 明るさを比べられるようにするためです。
  - Cycles、32サンプル
  - ワールド (.55, .60, .65)、強さ .7
  - 円形のエリアライト3つ。どれも (0, 0, 1.55) へ向けます。
    - 主光：(−2, −3, 4)、350W、サイズ4
    - 補助光：(2, −1, 2)、60W、サイズ3
    - 輪郭光：(0, 2, 3)、180W、サイズ3
  - ビューの変換は Standard、カメラは平行投影
  - 例：`outputs\claude-spa-attendant\source\render_views.py`
- **顔を似せるとき（Agent 47 など）**
  - 部位の寸法だけを合わせても、似ません。
  - モデルの輪郭を参照画像に重ねて比べます。参照画像は `hitman-web.jpg`（0.000498 m/px、中心 x = 964、頭頂 y = 258）です。
  - 比べるレンダーは、参考画と同じ照明（`CLEAN_HANDS_LIGHT=ref`：左から主光、黒背景）にします。
  - 面をボコボコにしすぎないでください。大きな面はなめらかにし、目・鼻・口の角だけ残します。
  - 案を複数出して、ユーザーに見比べてもらいます。
